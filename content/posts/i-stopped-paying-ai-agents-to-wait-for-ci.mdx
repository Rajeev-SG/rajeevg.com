One recent sequence in my coding-agent history took four GitHub Actions status-check cycles to answer whether CI had finished. Those cycles processed roughly **1.184 million model tokens**.

The agent was checking status. It had already reached the part of the job where a programme could wait for a result and branch on success or failure. Yet the model kept coming back into the conversation to discover whether anything had changed.

I have changed who owns that part of the work. After targeted checks and a push, the agent hands broad acceptance to GitHub Actions running on my own machine. The runner handles the tests, build, deployment wait and browser proof. A successful run should require no further model response.

This article is the first publication canary for that boundary. The numbers below are the baseline that prompted the change. They are not a measured before-and-after saving.

## What the session history showed

The AgentSessions analysis supplied for this change covered Codex sessions since **1 August 2026**:

| Measure | Observed baseline |
| --- | ---: |
| Sessions inspected | 632 |
| Tool calls | 20,632 |
| Wait calls | 4,557 |
| Model responses whose only purpose was processing a wait result | 612 |
| Raw model tokens processed by those wait-only responses | About 77.75 million |
| Cached input within that total | About 76.96 million |
| Output tokens from those responses | About 74,000 |
| Raw tokens attributed to GPT-5.6 Sol within the wait-only total | About 77.54 million |

The 4,557 wait calls and the 612 wait-only responses are different counts. A tool wait does not necessarily require a model turn, and a response following a wait can contain useful work. The narrower set isolates responses whose only purpose was dealing with the wait result. Nor should the whole wait-only total be labelled CI polling: the four-cycle GitHub Actions sequence is a specific example within the broader problem.

These are aggregate findings from my own session history. They describe activity in one setup, not a benchmark of every coding agent. My earlier [analysis of 551 Codex sessions](/blog/what-551-codex-sessions-reveal-about-real-ai-work) used a different sample; its counts should not be combined with this one.

The striking detail is the gap between the small amount of output and the volume of context processed to produce it. A short status response can still arrive at the end of a large conversation. Repeating that turn keeps bringing the conversation back through the model.

## Cached tokens still need an honest label

**77.75 million raw processed tokens does not mean 77.75 million fully billed fresh tokens.** About 76.96 million were cached input. Turning the raw total into a bill at a fresh-input price would badly misrepresent the evidence.

I am not claiming a precise cash saving, a measured latency reduction or that every token in the baseline can be eliminated. Billing and quota treatment depend on the route and account. The measurable waste here is unnecessary context processing and model turns, with quota and latency consequences that need their own accounting.

The [agent telemetry stack](/blog/the-agent-telemetry-stack) exists to keep those distinctions visible. Session activity tells me what the agent did. Cost and timing evidence answer different questions. A large token count is a reason to investigate the workflow, not permission to invent an invoice.

In [Token-maxxing](/blog/token-maxxing-getting-more-useful-ai-work-for-less-money), I argued for measuring accepted work against its total cost, including checking and retries. This is a concrete place to apply that idea. Choosing a cheaper model for a status check would reduce one part of the overhead. Moving the check into a deterministic job removes the need for that model turn altogether.

## The handoff has an explicit stopping point

The new contract is called `CI_HANDOFF`. It divides the work into five steps:

1. **Run targeted checks while editing.** The agent checks what it needs to make the next implementation decision. For this article, that means validating the frontmatter, MDX and internal links. Broad regression and deployment proof belong to the next stage.
2. **Push the implementation and emit `CI_HANDOFF`.** Record the commit, the checks already run and what CI now owns. End the authoring task at that boundary.
3. **Let local GitHub Actions own broad acceptance.** The self-hosted runner runs regression tests and the build, waits for deployment where required, and performs browser acceptance with evidence capture.
4. **Let green CI end silently.** The successful check and its artifacts are the result. No model wakes up to celebrate them or write another completion summary.
5. **Send failures to a cheap worker first.** A failure should produce a compact packet with enough evidence for a bounded repair. Escalate when diagnosis requires stronger judgment.

The last step is the intended failure route, not a claim that this article has already proved automated repair. A useful packet would identify the commit and failed job, show the failing command and a short error excerpt, and link to the full log or browser artifact. It should give the worker a specific problem without loading the entire successful run into its context.

This addresses one of the mechanisms in [Why agent systems become slow, expensive and fragile](/blog/why-agent-systems-become-slow-expensive-and-fragile): oversight keeps accumulating even after the useful implementation work is done. The stopping rule matters because “check once more” otherwise has no natural limit.

## What runs for this article

The repository's **Article local CI** workflow uses a self-hosted macOS runner. For article changes it owns the broad Vitest run and production build. Its regression command currently excludes a data-sensitive promoted-model snapshot test maintained through a separate workflow; “broad” does not mean every test without exception.

Before merge, the article workflow runs local browser proof. On a push to `main`, it waits for the Vercel check and then checks the production article. The article acceptance path covers desktop and mobile Playwright proof and captures artifacts for inspection. Those steps can wait and retry inside the runner without asking an authoring model to interpret each status update.

The authoring worker for this post has a narrower boundary: write the MDX, run proportionate content validation, commit locally and emit `CI_HANDOFF`. A controller integrates that commit. The worker does not push or poll GitHub Actions or Vercel. That local-commit boundary is how this publication exercises the wider post-push design without giving the authoring task ownership of integration.

The runner still consumes machine time. Tests still take time, deployments can still fail, and a broken acceptance job still needs attention. The change is that ordinary waiting has an owner that can finish without another inference request.

## What would count as a result

Publishing this post exercises the new path; it does not establish an exact controlled comparison. I have not run matched tasks through both workflows with the same context sizes, model routes, cache behaviour and failure conditions.

For this canary, the first question is whether the authoring worker stops at its declared boundary while CI produces the required acceptance evidence. A green run should have zero model turns whose purpose is to wait for it or announce its success. A failed run should return a small, actionable failure packet before a more expensive model is involved.

Across later publications, I want to compare post-handoff model turns and raw, cached and output tokens separately, alongside elapsed time and any repair work. If those turns fall but failures become harder to diagnose, the handoff needs work. If acceptance evidence goes missing, the workflow has not done its job.

For this article, the authoring task ends with a commit SHA and `CI_HANDOFF`. Whether the page builds, deploys and passes browser checks is work the runner must finish.
