I wanted to move most of the long execution token volume away from my Codex subscription without giving up the best part of Codex: a premium parent that understands the request, makes the hard calls, reviews the return, and decides when the work is actually done.

So I stopped treating the setup as a clever prompt and started treating it as a system that had to leave evidence behind.

The result is a split system. A native Codex task stays in charge. Fresh Codex tasks keep the parent context clean, while OpenCode Go handles bounded execution. That round trip works, but the savings story is not settled. A worker returns evidence and proposed work to the parent; it does not silently become the final answer.

That distinction matters. A component can work while the end-to-end claim remains unproven.

## Changing context is not changing provider

The top band of the diagram is about Codex Desktop context rotation. When a task grows long, the parent writes a compact durable pack and starts a genuinely fresh desktop task from it. That protects the working context from becoming a transcript landfill.

It does not move the work to another model. The fresh task is still Codex, with the same responsibility for understanding the request, setting boundaries, validating evidence, and deciding whether the job is actually done.

I initially got the rotation policy wrong. Fixed call-count gates and a phase-complete flag that was never consumed could rotate healthy work early, and repeated handoff attempts could create several Desktop tasks for the same job. The repaired policy looks at actual context pressure, stalled progress, elapsed time, and compaction pressure. Phase completion is an edge that gets consumed once, not a permanent alarm. Before creating a replacement, the system reserves an idempotent handoff keyed by task, phase, and pack, and reuses an equivalent continuation instead of creating another task. A high call-count ceiling remains only as an emergency brake.

The fresh-task seam is now proven for one end-to-end task. A new Codex Desktop task validated the pack without replaying the prior transcript, joined its Codex task and thread IDs to an NTM pane, OpenCode session, Bead, Agent Mail thread, and measured provider usage, then continued from the pack's exact next action. That is direct proof of the identity chain. It is not proof that every future rotation will be cheap or flawless.

One migration detail was easy to get wrong: a running session keeps the route it started with. A new configuration only applies to fresh sessions. During the transition, that made old and new routing appear to disagree even though both were behaving as configured. CLIProxyAPI was part of that migration history; it is not the active route shown here.

## Why composition beat bespoke coordination

Delegation begins with a bounded task packet, not a transcript dump. The packet carries the task ID, scope, constraints, done condition, evidence path, budget, and the runbooks the worker needs.

Each existing capability then gets one clear job. Native Codex task creation supplies the fresh parent boundary. Beads plus BVR hold durable task state, ownership, dependencies, checkpoints, and verification. NTM schedules and supervises the worker. Agent Mail carries compact acknowledgements, progress, blockers, reservations, and completion notices. OpenCode Go performs bounded execution. Telemetry connects task IDs, route decisions, counters, retries, and acceptance results. The older bespoke queue remains compatibility infrastructure for existing immutable packets only; it is not another coordinator to expand.

That composition won because every handoff already has somewhere to be checked. Agent Mail is not the scheduler and does not carry credentials. NTM is not the task database. A fresh Codex task is not a provider change. The parent can reject a wrong digest, an out-of-scope file, missing evidence, or a result that simply does not answer the request.

My default execution worker is OpenCode Go running Luna at high reasoning. The worker has to acknowledge both the task ID and the packet hash before it starts. Its output is not the final answer. It is evidence and proposed work that returns to the Codex parent for review.

That parent review catches a class of failure that a green command cannot. Did the worker touch files outside the packet? Did it return the evidence it promised? Do the changes answer the user's actual request? If scope, telemetry, or evidence breaks, the controller fails closed.

This is not theoretical. In one run, the worker produced useful reconnaissance but also touched an unrelated coordination path. The controller rejected the return. I used the clue to continue my own inspection, but I did not count that worker run as a successful completion.

## Why Go won over a larger routing experiment

I experimented with OpenRouter routing and with OpenCode subagents. The arrangement that held up was simpler: keep Codex as the premium planning and review surface, rotate to a genuinely fresh native task when its context gets crowded, and delegate bounded execution to OpenCode Go running Luna at high reasoning.

OpenRouter still has a narrow role. It does not supervise the system, and an ordinary worker failure does not silently select another model. The conditional routes separate two reasons to change models.

OpenRouter DeepSeek is a capacity fallback for text work. It is only eligible after a health gate says the normal Go route is unavailable. A failed or ambiguous health check closes the route instead of guessing.

Qwen has a narrower job. It is only eligible when the packet contains image-bearing work. It is not a general text fallback, and it does not become one merely because another provider is busy.

Keeping those gates separate prevents a blurry policy where any model can handle any task for any reason. The rules are simple enough to audit:

- Go/Luna is the default bounded execution route.
- DeepSeek is the health-gated text-capacity fallback.
- Qwen is vision-only.
- Premium Sol use requires an explicit recorded gate.

The gates themselves are proven. A complete live demonstration of fallback, reset, and return is still partial.

## What the measurements actually say

The cleanest matched canary completed all five checks on both routes. In that slice, Codex used 91,604 provider tokens and Go used 286,595. Go therefore used 3.13 times as many provider tokens and took about 2.30 times as long, while consuming zero Codex subscription tokens for the delegated execution slice.

That result is useful, but it is not a blanket efficiency claim. It says the subscription meter moved off Codex for that slice. It also says the substitute route spent more provider tokens and more wall-clock time.

The most useful directional figure came from completed tasks where both sides had attributable usage: Go represented 70.5% of the known token volume. That is much larger than the 9.7% Go share in the broader window and the corrected 18.75% Go share in the five-hour window.

Those percentages answer different questions. Their windows and inclusion rules are not interchangeable, so I do not average them or describe the difference as savings. The 70.5% completed-task share says the split can move most measured execution volume away from Codex in the work that completed with usable attribution. The 9.7% broader view says the overall system still spends far more on the parent side. The corrected 18.75% five-hour view lands between them and is another warning against using a single window as the headline.

The fresh-task proof also joined 605,429 measured OpenCode Go tokens across 17 calls to the same durable task ID used by Codex Desktop, NTM, Beads, and Agent Mail. That proves the identity chain. It does not prove that delegation caused a reduction in subscription usage. Without a matched baseline, the savings claim remains open.

Three substantial work slices completed after one retry each and then passed a native Sol review. That is meaningful evidence for the workflow. It is not enough to say delegated quality is always identical.

Another revealing number was 620 parent tool calls against a 120-call budget. That is a tool-call leak, not a provider-token total. Mixing those units would make the dashboard look precise while saying something false.

## Observability is useful before it is complete

The final band sends queue events, route decisions, provider counters, costs, retries, validation results, and handoff records into an observability layer. OpenTelemetry provides the trace shape; Langfuse gives me a place to inspect it.

Today that view is good enough to find missing counters, failed gates, and attribution mistakes. One fresh Desktop-to-worker task now has a complete durable identity join and appears in the live provider readout. The fleet-wide view is still incomplete, and concurrent jobs remain awkward because a plausible timestamp match is not the same thing as a durable identity.

The rule I care about most is mundane: unknown stays unknown. If a provider does not return usage, the field is null. If a join is missing, the dashboard says partial. That makes the system less impressive in a screenshot and much more useful when something goes wrong.

## What I would prove next

I would not spend the next round making the diagram prettier. The gaps are operational:

1. Interrogate recent session telemetry to explain why the five-hour Codex subscription limit is draining rapidly despite rotation and delegation.
2. Compare parent work before and after delegation, including tool-call volume, context growth, cache reads, worker share, and any routing or attribution failures.
3. Demonstrate a full health-gated fallback, recovery, reset, and return under controlled failure.
4. Give concurrent jobs durable identities so attribution does not depend on timing.
5. Run a representative matched Codex/Go/DeepSeek corpus with a hard parent budget and the same acceptance checks.

Only then would I make a whole-task savings claim. Until then, the honest conclusion is narrower: native fresh-task creation, Beads/BVR, Agent Mail, NTM/OpenCode Go, telemetry, rotation, and verification compose into an auditable system without a new bespoke coordinator. I can move bounded execution off Codex while keeping premium parent and review compute, and I can join that work back to the same durable identity. The 70.5%, 9.7%, and 18.75% figures are useful directional measurements, not causal proof.
