I wanted a simple thing: keep Codex in charge of the work while moving long execution stretches to cheaper capacity. The obvious fear was that I would save subscription usage by quietly lowering the quality of the result.

So I stopped treating the setup as a clever prompt and started treating it as a system that had to leave evidence behind.

The short answer is encouraging, but not clean. The delegation path works. The routing rules work. Several substantial tasks made the round trip and passed native Codex review. I still cannot claim that the whole system saves a particular multiple, or that every delegated result is indistinguishable from native execution.

That distinction matters. A component can work while the end-to-end claim remains unproven.

## Changing context is not changing provider

The top band of the diagram is about Codex Desktop context rotation. When a task grows long, the parent writes a compact durable pack and starts a genuinely fresh desktop task from it. That protects the working context from becoming a transcript landfill.

It does not move the work to another model. The fresh task is still Codex, with the same responsibility for understanding the request, setting boundaries, validating evidence, and deciding whether the job is actually done.

This rotation is only partially proven. The pack, manifest, and fresh-task launch are real. The last bit of the handoff still needs stronger automated evidence, especially around complete joins between the old task, the new task, and the work returned by a delegated worker.

One migration detail was easy to get wrong: a running session keeps the route it started with. A new configuration only applies to fresh sessions. During the transition, that made old and new routing appear to disagree even though both were behaving as configured. CLIProxyAPI was part of that migration history; it is not the active route shown here.

## The queue is the spine

Delegation begins with a bounded task packet, not a transcript dump. The packet carries the task ID, scope, constraints, done condition, evidence path, budget, and the runbooks the worker needs. The coordination queue then becomes the authoritative record of ownership and state.

My default execution worker is OpenCode Go running Luna at high reasoning. The worker has to acknowledge both the task ID and the packet hash before it starts. Its output is not the final answer. It is evidence and proposed work that returns to the Codex parent for review.

That parent review catches a class of failure that a green command cannot. Did the worker touch files outside the packet? Did it return the evidence it promised? Do the changes answer the user's actual request? If scope, telemetry, or evidence breaks, the controller fails closed.

This is not theoretical. In one run, the worker produced useful reconnaissance but also touched an unrelated coordination path. The controller rejected the return. I used the clue to continue my own inspection, but I did not count that worker run as a successful completion.

## Capacity fallback and visual routing are different gates

The third band separates two reasons to change models.

OpenRouter DeepSeek is a capacity fallback for text work. It is only eligible after a health gate says the normal Go route is unavailable. A failed or ambiguous health check closes the route instead of guessing.

Qwen has a narrower job. It is only eligible when the packet contains image-bearing work. It is not a general text fallback, and it does not become one merely because another provider is busy.

Keeping those gates separate prevents a blurry policy where any model can handle any task for any reason. The rules are simple enough to audit:

- Go/Luna is the default bounded execution route.
- DeepSeek is the health-gated text-capacity fallback.
- Qwen is vision-only.
- Premium Sol use requires an explicit recorded gate.

The gates themselves are proven. A complete live demonstration of fallback, reset, and return is still partial.

## What the measurements actually say

The cleanest matched canary completed all five checks on both routes. In that slice, Codex used 91,604 provider tokens and Go used 286,595. Go therefore used 3.13 times as many provider tokens and took about 2.30 times as long, while consuming zero Codex subscription tokens for the delegated execution slice.

That result is useful, but it is not a blanket efficiency claim. It says the subscription meter moved off Codex for that slice. It also says the substitute route spent more provider tokens and more wall-clock time.

One dashboard task recorded 5,166,631 Go tokens and a cost of $0.19260677. Two other jobs did not expose complete counters, so their values remain unknown. The telemetry pipeline stores those gaps as null rather than turning missing data into a zero.

Three substantial work slices completed after one retry each and then passed a native Sol review. That is meaningful evidence for the workflow. It is not enough to say delegated quality is always identical.

Another revealing number was 620 parent tool calls against a 120-call budget. That is a tool-call leak, not a provider-token total. Mixing those units would make the dashboard look precise while saying something false.

## Observability is useful before it is complete

The final band sends queue events, route decisions, provider counters, costs, retries, validation results, and handoff records into an observability layer. OpenTelemetry provides the trace shape; Langfuse gives me a place to inspect it.

Today that view is good enough to find missing counters, failed gates, and attribution mistakes. It is not yet a complete live join across every desktop rotation and delegated return. Concurrent jobs are especially awkward because a plausible timestamp match is not the same thing as a durable identity.

The rule I care about most is mundane: unknown stays unknown. If a provider does not return usage, the field is null. If a join is missing, the dashboard says partial. That makes the system less impressive in a screenshot and much more useful when something goes wrong.

## What I would prove next

I would not spend the next round making the diagram prettier. The gaps are operational:

1. Finish the telemetry joins from the original desktop task through rotation, queue ownership, worker execution, and parent acceptance.
2. Demonstrate a full health-gated fallback, recovery, reset, and return under controlled failure.
3. Give concurrent jobs durable identities so attribution does not depend on timing.
4. Run a representative matched Codex/Go/DeepSeek corpus with a hard parent budget and the same acceptance checks.

Only then would I make a whole-task savings claim. Until then, the honest conclusion is narrower: I can move bounded execution off Codex without giving up parent control, and I have evidence that the route can produce accepted work. The size and consistency of the saving are still open questions.
