I kept running into the same practical problem: Codex is useful for coding, but my subscription usage is limited. If I ask it to make every small edit, run every check, and tidy every file, I can use up that allowance before the job is done.

I wanted to keep Codex involved where judgement matters without asking it to do every repetitive step. So I split the work. The strongest Codex model in this setup, Sol, understands the request, makes the plan, and reviews the result. OpenCode Go uses a worker model called Luna to make the edits and run the checks. The hoped-for outcome is straightforward: use less Codex subscription capacity without accepting worse work.

## The short verdict

**Promising, but only partly proven.** In one small like-for-like test, the Go route moved 100% of the execution slice off Codex subscription tokens and passed the same five checks. The tradeoff was that Go used 3.13 times as many provider tokens and took about 2.30 times as long.

That is useful. It is not a miracle, and it does not prove the larger goal: a tenfold reduction in total Codex subscription usage with quality that cannot be distinguished from the direct route. The measurements cover different workloads and time windows, and the planning side still does too much work in some runs.

## The numbers that matter

The fairest result so far comes from one small test. I gave the same coding job to Codex and OpenCode Go, then ran the same five checks on both results.

The good news is real: Go can perform a coding job without consuming the Codex subscription allowance, and the checked result can be just as good on that task. The bad news is equally real: the Codex side still did far too much follow-up work during the larger project. That is why I cannot yet tell you the overall percentage saved.

## The manager and the workshop

The simplest mental model is a manager and a workshop.

The manager decides what needs doing, turns it into a safe job, checks the plan, and inspects the finished work. In my setup, that is Sol with Codex. The workshop does the hands-on work: it reads the relevant files, edits them, runs the narrow checks, and reports what happened. That is OpenCode Go, with Luna as the worker.

The manager does not need to watch every keystroke. It needs a clear job description and a trustworthy report. That leaves the expensive context for decisions rather than repetitive execution.

This does not mean Go is always cheaper. It means I can reserve Codex subscription usage for planning and judgement, then send suitable execution work through Go. The checks and review decide whether the work is good, not the product name.

### Is skill routing actually implemented?

**Partly, and the implemented part is real.** A routing policy maps the kind of task and its risk to a worker role, a set of skills, allowed tools, and whether Sol must review the result. The skill registry checks each selected skill's metadata, source path, hash, and health before dispatch. Tests cover examples such as bugs selecting diagnosis and test-driven-development skills, interface work selecting frontend and browser checks, and security or architecture work forcing Sol review.

The limitation is that this is currently strongest inside the bounded Go dispatcher. It is not yet a universal rule applied automatically to every possible Codex action, and the registry tests prove selected skills rather than every installed skill. So the accurate status is **working for routed Go jobs, with broader default adoption still in progress**.

## What is proven, promising, and unknown

### Proven

The matched canary passed the same 5/5 checks in both routes. Go handled 100% of that execution-only slice without Codex subscription tokens. Three substantial Go-routed slices also completed after one retry each and passed Sol review.

The larger jobs also passed substantial checks: 78 dashboard tests, 95 system checks, a final suite of 161 passing tests, and browser tests on desktop and mobile.

### Promising, but limited

The evidence suggests that splitting the work can preserve quality while saving Codex usage. It also suggests that OpenCode Go is best treated as cheaper execution capacity, not a faster or more token-efficient model.

### Still unknown

I still do not know the end-to-end saving because two larger Go jobs did not retain complete usage totals, and the Codex planning side did not retain a clean total for the same window. I also do not yet know whether quality remains indistinguishable across a broad mix of real tasks.

My honest assessment is: **the core idea works, but the main goal is only partly demonstrated.** Worker execution is saving subscription usage. Overall tenfold savings and indistinguishable quality remain unproven.

## What needs to happen next

1. **Measure every job completely.** Record Codex subscription usage, Go usage, cost, time, retries, and test results for the same start and end points. Missing counters are the biggest reason the overall saving is still unknown.
2. **Make Codex stop after planning and one review.** The 620-call closure run shows that too much hands-on work drifted back to Codex. Better worker reports and a hard parent budget should reduce that.
3. **Test a representative set of real tasks.** Run the same jobs through Codex-only and split Codex-plus-Go routes. Compare defects, human corrections, test results, time, and subscription use.
4. **Show the goal on one simple dashboard.** The useful headline is not total tokens. It is: “How much Codex allowance did we save, and did quality change?”
5. **Keep automatic backup routing.** When Go reaches its allowance, healthy OpenRouter workers should take over. When Go resets, new work should return automatically. Neither fallback should silently use Codex subscription capacity.

Once those measurements exist, the decision becomes simple. If the split route repeatedly uses around one tenth of the Codex allowance while matching the direct route's outcomes, the goal is met. If quality drops or Codex keeps absorbing the follow-up work, it is not.

## A mistake that changed how I migrate tools

I learned this by breaking the session that was doing the migration.

The active Codex process had started with `model_provider = "cliproxyapi"`. I changed the config on disk and moved the old CLIProxyAPI LaunchAgent, assuming the running process would follow the new route. It did not. A running session keeps the provider chain it received at startup. I had removed a path the parent session still needed, so recovery meant restoring the provider and restarting the old `8080 -> 18081/8319` chain.

The safer sequence is additive and staged:

1. Identify active consumers, including long-running sessions and child processes.
2. Add the new path without removing the old one.
3. Prove the new route with a fresh disposable session.
4. Send new work to it while old sessions keep their inherited route.
5. Let those sessions drain.
6. Prove the old provider, daemon, port, or LaunchAgent is unused.
7. Disable it only then, with a tested rollback path still available.

Changing `~/.codex/config.toml` affects future sessions. It does not rewrite the assumptions inside a process that is already running. That is obvious in a diagram and less obvious at one in the morning with several provider layers in motion.

## For technical readers

The worker receives a small written job containing the goal, allowed files, deadline, checks, and next action. A durable queue remembers who owns the job and where it stopped. Skills are selected from a checked registry rather than pasted into every prompt. Usage, retries, tests, and routing decisions feed the operator dashboard.

OpenCode Go is the normal worker route. If its allowance is exhausted, the system can use a health-checked OpenRouter worker without spending Codex subscription capacity. CLIProxyAPI remains available as a rollback path. New infrastructure is added and tested before old paths are removed.

That is the machinery. The reader-facing result should stay much simpler: Codex plans and checks; Go does most of the repetitive work; tests and evidence decide whether the result is acceptable.
